## Recommended domain wording

### EUR values and reimbursement totals

`EUR amount` is the stored EUR equivalent for an individual Expense, Advance, or MileageRecord, using that record's stored rate/calculation. Keep the term separate from report-total scope: all displayed totals are denominated in EUR, but different outputs sum different record types. PDFs can also show original-currency amounts beside the EUR equivalents.

The PDF reimbursement statement should be scoped to the generated PDF summary: `sum(expense.amountEur) + dailyAllowance - sum(paidAdvance.amountEur)`. `PdfService.kt:563-568` explicitly excludes mileage from this summary; mileage remains listed in its own section (`:402-499`). **The API report DTO currently uses a different calculation**: `ReportMapper.kt:107-111` computes `totalReimbursable = expenses + allowance + mileage - paid advances`. Avoid describing the API field and PDF summary as one shared “net settlement” value. This is a current source/documentation semantic split, not a tested accounting outcome.

`CONTEXT.md`'s statement that all report totals/PDFs/dashboards are “expressed in EUR” is true as a denomination rule, but it can be read as saying their included components agree. Make clear that components differ by output. Dashboard manager monthly spend is SQL expense spend (`DashboardController.kt:159-168`); its recent-activity amount is also expenses-only (`:172-190`).

### OCR source lifecycle

Suggested wording: “An OCR source is the durable, technician-owned upload attached to an OcrJob before an Expense/Receipt exists. When OCR returns a result (including partial/missing details), the pipeline advances the same job through Expense and Receipt stages; it creates a draft Expense, then a Receipt, and deletes the source after receipt promotion commits. Cancellation also attempts to delete the source. A provider/processing failure that exhausts retries marks the job permanently failed and currently leaves the source associated with that job; it does not automatically create a photo-only Expense. A 30-day `expiresAt` timestamp is written at job creation, but current backend code does not enforce job expiry or clean up expired-job sources.”

Evidence: `OcrController.kt:95-107` stores the source, sets `expiresAt` +30 days, then marks the job pending. `AsyncOcrService.kt:155-165` completes the OCR stage for partial results; `:174-233` creates a draft; `:236-281` creates the receipt and deletes the source only after commit. Generic failures become `PERMANENT_FAILURE` after three attempts (`:284-300,323-325`) without deleting the source. Cancel attempts cleanup (`:68-98`). `OcrJobRepository.kt:29-43` finds **expired leases** (`status='PROCESSING'` and `lease_until<=now`), not jobs whose `expires_at` elapsed; search found no other consumer of `expiresAt`/no expiry transition. `findExpiredJobIds` is used for worker recovery (`AsyncOcrService.kt:53-56`).

The visible “Needs Review” state is a UI-derived signal, not a persisted Expense status, consistent with ADR-0004. Backend OCR drafts use `status="draft"` (`AsyncOcrService.kt:203-219`); the normal asynchronous path creates amount zero if extraction omitted amount. Do not claim the permanent provider-failure path automatically promotes the file to a photo-only Expense.

### Roles and lifecycle

Use the persisted role names: `technician`, `manager`, `chef_finance`, and `mod` (Moderator/admin label). `Authorization.kt:21-29,56-81` says `manager` and `chef_finance` can manage/approve/reject, `chef_finance` alone can pay, and `mod` can view all but cannot manage or pay. `ExpenseReportLifecycle.kt:95-175` confirms approval/rejection use `canManage`; report pay uses `canPay`. Thus README’s generic “manager reviews” should say **manager or chef_finance reviews/approves/rejects; chef_finance marks an approved report paid**. A `mod` is an admin for viewing/configuration, not an approval role.

`recall` accepts submitted or rejected reports and returns them to draft, clears `submittedAt`, but does not clear rejection/signature fields (`ExpenseReportLifecycle.kt:77-92`). Rejection changes attached expenses back to draft (`:141-149`); Expense update/delete/upload guard only the Expense status, so those expenses can be edited while the parent report remains rejected (`ExpenseService.kt:168-179,289-300,332-343`). These are source-confirmed behaviors; whether rejected reports must be recalled before editing is a business-rule choice.

The “Technician … reimbursed for exact EUR amount debited from their bank” glossary statement is policy/intent, not a backend guarantee. The API persists a rate and `fx_rate_manual` flag; no distinct debited-amount field exists. The UI can derive a manual rate from a user-entered debit amount (`FxRateInput.tsx:69-98`), and backend stores the supplied manual rate (`ExpenseService.kt:95-108,134-150`).

## README and root-context claims to amend or qualify

- `README.md:64` says Spring Boot 3.4; `backend-kotlin-jpa/build.gradle.kts:5` is Spring Boot 3.5.16. Java 21, PostgreSQL 16, and Redis 7.4 are represented in source/config (`build.gradle.kts:13-16`, `docker-compose.yml:3,25-26`).
- `README.md:34-57` lists roles generically and payment state loosely. State the canonical roles and lifecycle duties above. Draft reports can be empty; submission requires at least one attached Expense (`ExpenseReportLifecycle.kt:50-60`).
- `README.md:198-210` presents receipt upload as a single flow ending in a draft Expense response. The durable async OCR endpoint creates an OcrJob and may return pending/accepted before later stage promotion (`OcrController.kt:120-129`); document the sync and async routes separately.
- `README.md:213-222` says distributed work is processed “once or retry[ied] within the attempt limit.” This overgeneralizes. OCR has a three-attempt terminal-failure policy; storage migration is capped; Technician email ingestion keeps transient failures retryable with capped backoff and has no terminal attempt-count cap. Prefer “durable claim/lease or ledger prevents duplicate committed effects; retries/backoff and terminal conditions are workflow-specific.” ADR-0002 also explicitly documents at-least-once Expense create/upload recovery, not exactly-once behavior.
- `README.md:486-499` storage rules are stated as a universal invariant, but Insurance uploads bypass `StorageContext`: `InsuranceController.kt:92-115` checks extension/size and writes through `uploadFile` without magic-byte validation. Download hardening is present (`:157-173`: safe extension-derived MIME, attachment, `nosniff`). `StorageService.storeFile` enforces size/extension/magic bytes for RECEIPT/OCR_SOURCE/SIGNATURE contexts (`StorageService.kt:27-55,270-300`). Scope the guarantee to the contexts that pass through that seam.
- `README.md:493` says the authoritative limiter protects report-export workloads. `RateLimitingFilter.kt:31-42,58-63` limits login, refresh, OCR scan, expense scan, bulk upload, and `/api/reports/{id}/pdf|receipts-zip`; the `/export` path named in the audit is not matched. The matched PDF/ZIP rule falls back to 15/minute (`:60-63`), not 5/minute. The base application.yml default is in-memory (`application.yml:54-60`), while the production profile configures Redis and fail-closed behavior; describe the store as profile-dependent rather than implying production uses the base default.
- `README.md:494` says forwarded IP headers are trusted only from configured proxies; the custom filter itself gates them on `request.remoteAddr` being in configured `trusted-proxies` (`RateLimitingFilter.kt:83-99`), but `application.yml:88` also enables framework forwarded-header handling. End-to-end spoof resistance depends on filter ordering and ingress sanitization; it was not reproduced. Document the config boundary as a source-level control, not verified production protection.
- `README.md:94` rule 5 (external calls outside transactions) is a design rule, but not current implementation reality. Expense create/update call FX inside `@Transactional` methods (`ExpenseService.kt:88-100,168-200`); Advance create/update/pay and Mileage operations also call FX in transactional handlers. Email’s durable path parses before `createReportAndComplete`, but legacy `processIncomingEmail`/`simulateIncomingEmail` still include AI parsing under `@Transactional` (`EmailImportService.kt:403-425,490-532`). Label as an invariant with known exceptions/gaps, not completed architecture.
- `README.md:538-540` says failed email is retryable only within a configured attempt limit. This conflicts with ADR-0003 and current `TechnicianEmailIngestionService.kt:115-166`: failed processing and acknowledgements receive capped exponential backoff, and do not become terminal solely by attempt count. Missing/permanently invalid sender/content is rejected and acknowledged; explicit admin retry is a separate path (`:71-105`, `ImapIngestionLedger.kt:216+`).
- `README.md:602-610` says dashboard endpoints use SQL aggregates instead of hydrating month-wide expenses. This is true for monthly spend KPI (`DashboardController.kt:159-168`), but manager recent activity still loads all reports-with-expenses before `.take(10)` (`:172-190`). Similarly, settings are not fully centralized: `ReportMapper.kt:83-95` reads `daily_allowance_rate` directly from `AppSettingRepository` and queries it once per report mapping (`:94`); do not say all daily allowance reads are owned/cached by `AppSettingsService`.
- `README.md:521-540` OCR/provider descriptions are broadly consistent with ADR-0006 (mod-managed chains, controlled result contract, fallback), but the global OCR toggle/local-parser detail should be linked to code/docs and kept separate from the async job guarantee above.
- `CONTEXT.md:32` is sound as a general canonical EUR value, but qualify output scope as above. `CONTEXT.md:65` currently overstates OCR-source cleanup after expiry; replace with lifecycle wording above. `CONTEXT.md:81` is useful, but restrict the mileage exclusion to the PDF summary; do not apply it to `ReportOut.total_reimbursable`.

## `FULL_APP_AUDIT.md` backend disposition

- **BE-01 orphan cleaner:** Supported and high risk, with narrower trigger/effect: `scanOrphanReceipts` only reports candidates; `cleanOrphanReceipts` deletes them (`AppSettingsService.kt:273-303`). The scan recursively includes all local files except `cache`, compares only receipt paths, and so classifies insurance files and active OCR source files as orphans. `ReceiptRepository.findAllFilePaths` is subject to `@SQLRestriction(deleted=false)`, so soft-deleted receipt paths are omitted. Report source evidence does not prove this has happened in production. Do not say scan itself deletes, or that remote-only files/all documents are deleted.
- **BE-02 open transactions during external I/O:** Partial/credible on cache misses as described above; external timing, pool size 10, and application-wide exhaustion were not verified. OCR locking was fixed. Legacy email parsing methods are distinct from the active durable scheduler path.
- **BE-03 N+1/OSIV:** Partly supported. Lazy collections are traversed, but batch size 16 already exists; no query counts measured. Direct daily allowance lookup per report remains. OSIV is not disabled in application.yml, but profile/runtime overrides unknown.
- **BE-04 exception mappings:** Partly supported. Catch-all is 500; common validation, malformed JSON, missing params, type mismatch, `ResponseStatusException` have explicit 400/status mappings (`ValidationExceptionHandler.kt:37-77`). No max-upload, integrity, or optimistic-lock mapping. Multipart is 10 MB, not 15 MB. HTTP results not integration-tested.
- **BE-05 lifecycle/RBAC:** Mostly source-supported with qualifications: mod can create paid advances and mutate draft-report advances via `canViewAll`; paid-advance deletion is only permitted for draft reports. Requested-advance update is incomplete/narrow as noted. Rejected expenses editable; recall leaves metadata. Bulk failure may leave an expense after separately committed creation. Business choice required on rejected edit/metadata reset.
- **BE-06 mixed items:** backup script claim is false (verification doc says direct `pg_dump -Fc`, strict shell options already present; database-only scope remains; scheduling/off-host/volume backup are runtime deployment questions). FX `sourceDate` cache risk supported. Async+scheduled overlap is plausible, but ledger prevents duplicate durable effects. Email index is nonunique and `User.email` lacks a unique constraint. `getLocalPath` may return missing target after remote failure, S3 client close gap and PDF path disclosure are supported.
- Security production claims in audit: known credentials/accounts, public spoof exploit, host backup status, actual proxy sanitization, public headers, deployed config/version and live data are not source-provable and were not tested. Keep them explicitly unverified. The existing verification doc already properly qualifies several of these.
