# Durable identity for keyed Expense and Receipt saves

Supersedes ADR 0002's deferred-idempotency limitation **only for keyed Expense creation and Receipt attachment**. A successful save and its replay snapshot commit in one PostgreSQL transaction under an owner/operation/key identity. We retain identities without TTL or an Expense/Receipt foreign key: deleting a resource or replaying an old offline queue item must not create a replacement. Requests without a key remain at-least-once; this does not cover OCR job acceptance, duplicates with a new key, or lost browser-local data.

## Consequences

- `POST /api/expenses` and both Receipt upload routes accept `Idempotency-Key` (1–256 ASCII letters, digits, `.`, `_`, `:`, `-`). Bulk upload accepts up to 200 characters, reserving room for its public Receipt-retry suffix. Missing headers preserve legacy behavior. Reusing a successful key with different DTO data returns 409; fingerprints include decimal representation, so callers must replay the same serialized data rather than silently revising a pending save.
- The frontend staged queue derives creation and attachment keys from its committed immutable record ID (`${id}:expense`, `${id}:receipts`), preserving them across reload, lease handoff and response-loss retries. Existing unkeyed attempts cannot be deduplicated retroactively.
- Receipt upload binds the ordered filename/content-type/size/SHA-256 manifest before committing one file per independent transaction. Replaying an incomplete batch skips committed files and retries failed stages; changing content/order/count with the same key returns 409. The same key works on `/receipt` and `/receipts`. Current owner/draft authorization is rechecked; a deleted or no-longer-editable Expense is not replaced.
- Bulk upload binds its source manifest, persists one authoritative Expense identity per source index, and attaches with `${batchKey}:receipt:${index}`. Attachment errors return `expense_id` and zero-based `file_index`; clients retry only attachment on that known Expense with that same derived key. Successful rows include Receipt metadata. Whole-batch replay returns current Expense state, may retry failed stages, and is not a frozen batch response.
- Bulk OCR runs outside identity transactions. Concurrent initial requests may duplicate provider work, but PostgreSQL uniqueness and row locks permit only one Expense per source identity. A replay after committed creation bypasses OCR. Sources rejected for size are represented by rejection metadata rather than reading oversized bytes.
- Ledger SQL uses the same transaction manager/connection as JPA writes. Successful response snapshots and resource rows commit together; failed stages roll back together. Filesystem/S3 cannot share the database transaction: existing rollback cleanup remains best effort, and a process crash may leave an unreferenced file. This decision promises no duplicate persisted Expense/Receipt rows for the same keyed stage, not exactly-once external storage or OCR calls.
- Retained snapshots contain historical Expense data. Do not add opportunistic cleanup or TTL without a separate retention/privacy policy and a tombstone design that preserves save identities. Rollback to old application code leaves the additive V104 table intact, but old code does not honor these keys and is again at-least-once.
